## 2026-10-05, ночь — Этап 5: подача

- **День завода в демо закреплён: 05.10.2026, 10:30** (`live.start_date` в `config/plant.yaml`). Раньше это был последний рабочий день по часам компьютера, и цифры в интерфейсе менялись бы от дня показа. Теперь они совпадают с презентацией, `BUSINESS_CASE.md` и видео. Переопределить можно через `ALLUR_LIVE_START` или `start_date: null`.
- **Денежный эффект — через вклад машины в маржу, а не через выручку:** 350 тыс. ₸, ≈5% средней розничной цены ≈7,05 млн ₸ по публичным ценам Onix, Cobalt и J7.
  - Три сценария реализации верхней оценки: 25%, 50% и 80%.

- **Резервное видео демо** записано автоматически (Playwright, 1920×1080, подписи на экране), сжато в MP4 около 5 МБ и лежит в `docs/video/`. Видео с голосом для подачи пишет команда.
- **Презентация** — 12 слайдов, полная, чтобы читаться без выступающего при онлайн-отборе. На защите выступающий проходит по слайдам 2–3, затем демо, затем 9–10 и 12.
- **После отказа станка риск на экране сбрасывается** до окончания ремонта. Иначе «98%» висел на стоящем конвейере.

## 2026-10-05, ночь — Этап 4: ИИ

- **LLM — бесплатные Groq и Google Gemini вместо Claude API** (решение команды: нужен бесплатный сервис).
  - Ключи `GROQ_API_KEY` и `GEMINI_API_KEY` берутся из `.env`.
  - Порядок: Groq, затем Gemini. Модели по умолчанию:
    - Groq — `openai/gpt-oss-120b`, запасная `llama-3.3-70b-versatile`;
    - Gemini — `gemini-3.5-flash`, запасная `gemini-3.1-flash-lite`.
  - Модели и порядок меняются переменными, без правки кода.
  - Claude остаётся инструментом разработки (раскрывается в `docs/TECH.md`).
- **Цифры считает код, LLM пишет текст.** Числа в тексте LLM сверяются с расчётом. Без ключа выводы те же, но текст по шаблону.
- **Кэш ответов LLM** — `data/ai_cache/`, в git не попадает. Перед показом двойник запускается один раз с интернетом.
- **Выводы ИИ считаются по закрытым сменам** (30 дней до начала текущей смены). Они не «прыгают» каждую секунду, а после сброса демо попадают в кэш.
- **Прогноз отказов:** LightGBM — только для цепей конвейеров. Для печи — правило «разброс температуры ×2», роботы и стенды не прогнозируются. Причина — проверка в `docs/ML_REPORT.md`:
  - модель на печи поймала 0 из 7 сбоев, правило — 6 из 7;
  - на роботах ROC-AUC 0,52.
- **Горизонт прогноза** — 2 часа работы, оценка раз в 5 минут. Предупреждение открывается после 2 оценок подряд выше порога 0,7 (подобран на отдельной истории).
- **Обучение** — `make train`, около 3 минут. Это 5 независимых «лет» по 150 суток: обучение, валидация и проверка на разных seed. Модель хранится текстом LightGBM (`data/models/failure_lgbm.txt`) и коммитится. Классификатор отчётов обучается при первом запуске за секунду (файл в .gitignore — зависит от версии sklearn).
- **Сценарий «Износ цепи»** удлинён: предвестник 40 минут работы вместо 25. Так ИИ успевает предупредить заранее, и это видно на показе.
- **Эффект выводов** — в автомобилях за месяц: минуты, возвращённые в смены, делятся на плановый такт 4 мин. Это верхняя оценка («до N авто»), так и написано в допущениях.
- **Месячная цель 5500 почти равна пределу двух смен** (≈5558 при идеальном цикле). Прогноз показывает вероятность выполнить цель честно, около 0%. Выводы показывают, сколько дают меры, а остаток закрывают субботние смены (D10).

## 2026-10-05, вечер — Этап 3: интерфейс

- **Стиль:** светлая «студийная» изометрия по референсу команды.
  - Холодный светло-серый пол `#e3e7eb`, белые панели, сигнальный оранжевый `#ef8a14` (роботы, главный акцент).
  - Шрифты IBM Plex Sans и Plex Sans Condensed (крупные цифры и заголовки).
  - Без моноширинных подписей, ПРОПИСНЫХ меток и тёплого кремового фона.
- **Карта — собственный SVG** с изометрической проекцией. Планировка — U-образная линия:
  - верхний ряд: склад → сварка → окраска;
  - поворот конвейера;
  - нижний ряд: сборка → контроль → склад готовой продукции.

  Расстановка оборудования условная — это написано в подписи к карте.
- **Страница цеха** открывается панелью поверх карты, а не отдельной страницей: контекст завода остаётся виден слева.
- **Парето причин простоев:** «ожидание соседних участков» (нет входа, выход занят) вынесено из графика в отдельную строку. Иначе оно забивает реальные причины.
- **Лента событий** показывает аварии, ТО, переналадки и восстановление оборудования. Частые переключения «ждёт / работает» видны только на шкале.
- **Отчёт рабочего** дополняет свежую остановку станка (идёт сейчас или закончилась не больше 2 ч назад) или запись, выбранную в журнале кнопкой «Заполнить». Старые черновики не перехватываются новым отчётом.
- **Сценарии демо** доступны с этапа 3: `sensor_fault`, `chain_break`, `filter_clog` — `GET /api/scenarios`, `POST /api/scenarios/{name}/trigger`, кнопки в пульте (клавиша D).

## 2026-10-05, вечер — Этап 2: бэкенд и живой режим

- **Время завода в демо:** последний рабочий день, 10:30 (`live.start_time`), а не часы ноутбука. Демо одинаково в любой день; на Demo Day (пятница, 16.10) дата совпадёт с реальной.
- **Прогрев — 30 суток** до «сейчас»: история для Парето, графиков и инцидентов. Старт сервера около 5 с.
- **Скорости** ×1/×10/×60/×300, по умолчанию ×10: при ×1 кузов проходит участок за 4 минуты, на показе это слишком медленно.
- **Мгновенный сброс:** запасной прогретый мир строится в фоне. Сброс — около 0,2 с (требование чек-листа — меньше 5 с).
- **OEE завода** — среднее по сварке, окраске и сборке; **выпуск завода** — кузова после контроля качества.
- **Новое состояние оборудования `idle`:** станок исправен, но участок остановлен другим оборудованием.
- **Правила инцидентов:** брак — только после 40 кузовов и 3 дефектов за смену, иначе первый же дефект даёт 3% и ложную тревогу. Лимит простоя считается по незапланированным остановкам критического оборудования.
- **Хранилище:** SQLite (SQLAlchemy) для отчётов, инцидентов и импортов. Живое состояние и телеметрия за 24 ч — в памяти, история — в parquet.
- **Истинные причины симулятора** хранятся в БД для оценки ИИ, через API не отдаются.

## 2026-10-05, вечер — Этап 1: симулятор

- **Тестовые данные — вымышленные и не секретные** (подтвердила команда). Репозиторий остаётся публичным, `data/raw` и `data/test` коммитим. Пункт 9.4 положения к ним не относится.
- **Участок — последовательная станция:** один кузов за цикл; остановка любого оборудования останавливает участок (D5). Остаток цикла дорабатывается после ремонта или в следующую смену.
- **Отказы** разыгрываются по наработке (Вейбулл). Предвестники есть у износовых отказов: цепь, горелка, фильтр. Сбой датчика ABB внезапный, это честно непредсказуемо.
- **Фильтр камеры окраски** засоряется: перепад давления 120 → 450 Па. Выше 300 Па растёт сорность; на пределе — вынужденная замена около 40 минут. Так объясняются брак окраски 3,5–5,2% и «Замена фильтра 40 мин» из данных.
- **Плановое ТО** делается в начале первой смены, как сейчас (ТО ABB-04 в данных). Режим `night` — альтернатива для «что если» и для рекомендаций ИИ: ночью завод не работает (00:00–08:00), поэтому ТО там не стоит выпуска.
- **Рекомендации ИИ** формулируются как «перенести в нерабочее окно (ночью)», а не «в пересменку»: смены 08–16 и 16–24 идут без разрыва.
- **Демо-допущения A5–A9** (в `config/plant.yaml`):
  - A5 — циклы участков 3,88–3,92 мин;
  - A6 — интервалы ТО: роботы и камеры 160 ч, конвейеры 200 ч, печь 240 ч, стенды 300 ч;
  - A7 — ресурс фильтра 125 ± 25 моточасов;
  - A8 — партии моделей по 40–80 кузовов, переналадка 3–7 мин;
  - A9 — микроостановки 1–3 мин, в среднем раз в 150 мин, записываются в 5% случаев.
- **Отчёты рабочих синтетические:**
  - 90% заполнены, 15% причин выбраны неверно, часть текста с опечатками;
  - истинная причина хранится отдельно и служит только для оценки ИИ.

## 2026-10-05, вечер — Положение хакатона и идеи команды

**Причина:** получено положение хакатона и предложения тиммейта.

- **Дедлайн подачи — 8 октября 23:59** (п. 1.6, 5.3). Сдаём:
  - PDF-презентацию;
  - прототип или видео;
  - репозиторий или архив;
  - описание архитектуры, данных, технологий и библиотек с AI-инструментами;
  - эффект, ограничения и условия внедрения.

  План сжат: этапы 1–5 до 8.10, финальная полировка — 9–15.10.
- **Защита — 3 минуты с демо плюс 3 минуты вопросов** (п. 5.6). Демо внутри питча — не больше 90 секунд, один сквозной сюжет.
- **Критерии в баллах** (п. 7.1). Больше всего весят техническая реализация (20) и потенциал внедрения с эффектом (20, решает при равенстве баллов). Отсюда отдельный слайд с планом пилота и условиями внедрения.
- **Концепция расширена до «Цифровой двойник + ИИ-помощник»** — по идеям команды:
  - **второй источник данных — люди:** рабочие при простое указывают причину и описание (планшет у линии, позже Telegram-бот);
  - **ИИ анализирует отчёты** вместе с данными станков — по цеху и по компонентам, связывает простои с браком и ТО;
  - **изометрическая карта завода** с кликабельными цехами;
  - **страница цеха:** время до планового ТО, статистика простоев и причин, графики;
  - **вкладки** «Завод», «Мониторинг», «Прогноз», «Простои», «Данные завода».
- **Стиль интерфейса — светлая изометрия** с оранжевыми акцентами, как в референсе команды. Тёмная тема этапа 0 заменяется. Довод: светлые интерфейсы лучше читаются на проекторе.
- **ИИ-анализ отчётов:** Claude API со структурированным ответом, кэш ответов для офлайн-демо, офлайн-фолбэк — TF-IDF + логистическая регрессия и правила.
- **Telegram-бот, «что если», прогноз узкого места через перемотку, аномалии** — после 8.10, если пройдём в финал.
- **Данные партнёра** (п. 9.4): непубличные данные нельзя класть в открытый репозиторий. Рекомендация — сделать репозиторий приватным до первой загрузки. Решение за командой.
- **Генеративный ИИ** (п. 6.4): Claude указывается в `docs/TECH.md` как инструмент разработки. Для команды ведётся `docs/EXPLAIN.md`, чтобы отвечать жюри по коду.

## 2026-10-05 — Техника

- Стек:
  - симулятор — Python + SimPy;
  - бэкенд — FastAPI;
  - ML — scikit-learn и LightGBM;
  - фронтенд — React 18, Vite 6, TypeScript strict, Tailwind 4, ECharts 6, Zustand.
- ECharts 6, а не 5: в 5.x есть уязвимость XSS (GHSA-fgmj-fm8m-jvvx). `echarts-for-react` 3.0.6 поддерживает 6.x.
- Шрифты IBM Plex Sans и Plex Mono подключены из npm (`@fontsource`), без Google Fonts. Демо должно работать без интернета.
- `make demo`: бэкенд сам отдаёт собранный интерфейс из `frontend/dist`. На ноутбуке выступающего нужен один процесс и один порт (:8000).
- В коде и API идентификаторы оборудования ASCII (`CAM-02`), в интерфейсе — названия из данных («Камера-02»).
- Время везде в UTC+5 (Костанай). Часы в интерфейсе не зависят от часового пояса ноутбука.
